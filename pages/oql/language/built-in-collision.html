Built-in Name Collision

Visibility

Owner: omega | Workspace: OmegaAI | Visibility: Public

What this is

OQL has a set of built-in term solvers — terms like http-endpoint, http-request, uuid, time-now — that are resolved by the engine before any datastore lookup. When you declare a defterm (or a functor) whose name matches a built-in term solver, the built-in wins silently. OmegaDB does not warn. Reads against the datastore return wrong results or no results with no error.

The production example

In the http-hook implementation, a registry defterm was given the functor name "http-endpoint":

(defterm Qo.Data.HttpHookRegistry
  {"name"        "http-endpoint"
   "args"        ["Loc" "Id" "Func"]
   "primary-key" ["Id"]})

OQL has a built-in term solver also named http-endpoint (no !). When a read query ran against the datastore:

(DS/http-endpoint Loc Id Func)

…the engine dispatched the built-in solver instead of the defterm read path. The built-in http-endpoint performs live endpoint registration, not a datastore read. The query returned wrong results silently — no error, no warning, no indication that the wrong solver fired. Fix: rename the defterm functor to "http-ep" so it no longer collides.

The hard rule

Defterm functor names must not collide with any built-in term solver name. When they do, the built-in wins — silently, at every call site. OmegaDB has no detection or warning for this collision. The failure mode is silent wrong results, which is harder to diagnose than an error.

Known built-in term solver names

The following names are reserved by the engine. Do not use any of them as a defterm name, functor name, or clause head:

Built-in nameWhat it does
http-endpointRegisters an HTTP endpoint handler. Returns {"id" EndpointId}.
delete-http-endpointUnregisters an HTTP endpoint by id.
http-requestMakes an HTTP request. See Built-in Terms § HTTP.
uuidGenerates a new UUID string.
time-nowReturns the current ISO timestamp.
throwRaises a typed OQL exception.
returnReturns results from a query.
definedTests whether a symbol is bound.
randRandom double in [0.0, 1.0).
rand-intRandom integer in a range.
enable-full-scan / disable-full-scanBookends for Mango full-scan queries.
mango-queryExecutes a raw Mango query against a datastore.
json-stringifyBidirectional JSON ↔ string conversion.
string-split, string-concat, string-contains, string-replace, re-find, string-formatString operations.
get, get-in, set, merge, select-keys, zipMap operations.
get-list, length, append, concat, partitionArray operations.
+, -, *, /, >, <, >=Arithmetic / comparison.
fold, with-unique-by, with-order-by, with-group-by, with-count, with-limit, with-skip, with-sortReducers. See Reducers.
when, when-not, if, with-table-ifControl flow. See Control Flow.
run-term, callClause invocation primitives.
run-page, set-dataPage/data operations.
prop-vals-by-folder, row-index, sec-indexDatastore read primitives.
write-table, delete-rowsDatastore write primitives.

Note: This list covers known built-ins at the time of writing. It may not be exhaustive — the engine's internal resolver can claim any name it recognizes. If you observe silent wrong results or unexpected behavior from a newly named functor, check whether the functor name matches anything in the built-in term vocabulary.

How to avoid the collision

  1. Use a domain-scoped functor name. Names like "http-ep", "hook-registry", "my-endpoint-record" are safe. Single-word names that match common verbs or nouns ("endpoint", "request", "hook", "get", "set") are likely to collide now or in a future engine release.
  2. Test reads immediately after declaring a new functor name. After adding a defterm or functor, push and run a probe that reads from the datastore. If the read returns no results or unexpected data with no error, suspect a built-in collision and rename.
  3. Prefer namespace-prefixed functor names in production code. A name like "http-hook-data" is far less likely to collide than "http-endpoint".

Why the engine does not warn

OQL's term resolution dispatches to the built-in solver before checking datastores. The engine treats the built-in match as a normal successful dispatch — it does not know a defterm with the same name exists at the application layer, so it has nothing to warn about. This is a structural gap, not a missing warning log. Until the engine adds a registration-time conflict check, name collision avoidance is the author's responsibility.
